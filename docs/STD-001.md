# 2. Descripción general del proyecto

## 2.1 Nombre del sistema

**LOCUSTAF (Locus Staff)**

Sistema web de gestión de asistencia laboral desarrollado con Flutter Web y Firebase.

---

## 2.2 Visión del producto

LOCUSTAF es una plataforma orientada a la administración del personal de una organización, permitiendo gestionar empleados, lugares de trabajo, registros de asistencia, justificativos, incidencias, reportes y perfiles de usuario desde una única aplicación.

El sistema busca reemplazar procesos manuales de control de presentismo mediante una solución moderna, segura y escalable.

La aplicación utiliza geolocalización para validar la presencia del empleado en lugares de trabajo autorizados y registrar movimientos de asistencia con información confiable.

---

## 2.3 Objetivo principal

Construir un sistema profesional de control de asistencia laboral que permita:

* Registrar ingresos y egresos.
* Validar ubicación del empleado.
* Administrar personal.
* Gestionar lugares de trabajo.
* Controlar incidencias.
* Administrar justificativos de inasistencia.
* Generar reportes.
* Proporcionar información útil para la toma de decisiones.

# 6. Principios generales de desarrollo

## 6.1 No romper funcionalidad existente

Toda nueva implementación debe conservar las funcionalidades previamente aprobadas.

Antes de modificar un módulo existente deberá analizarse su impacto.

---

## 6.2 Reutilización

Antes de crear nuevos componentes debe verificarse si existe una implementación reutilizable.

Debe evitarse:

* Providers duplicados.
* Servicios repetidos.
* Lógica de negocio duplicada.
* Modelos redundantes.

---

## 6.3 Responsabilidad única

Cada componente debe tener una responsabilidad clara.

La interfaz gráfica no debe contener reglas de negocio.

Los repositorios deben encargarse del acceso a datos.

Los servicios deben encapsular lógica reutilizable.

---

## 6.4 Evolución controlada

Los cambios estructurales importantes deberán justificarse técnicamente.

No se deben realizar modificaciones arquitectónicas únicamente por preferencias personales.

---

# 11. Modelo de usuarios y roles

LOCUSTAF utiliza un sistema basado en roles para controlar las capacidades disponibles dentro de la aplicación.

Los roles principales son:

* Administrador.
* Supervisor.
* Empleado.

La autorización debe validarse tanto en:

* Interfaz de usuario.
* Navegación.
* Reglas de Firebase.

La seguridad no debe depender únicamente de ocultar botones o pantallas.

---

# 11.1 Administrador

El administrador posee control completo sobre la organización.

Responsabilidades:

* Gestionar empleados.
* Gestionar usuarios.
* Crear y modificar lugares de trabajo.
* Configurar parámetros del sistema.
* Administrar incidencias.
* Revisar justificativos.
* Consultar reportes.
* Gestionar permisos.

El administrador representa el usuario con mayor nivel de privilegios.

---

# 11.2 Supervisor

El supervisor posee permisos operativos limitados.

Puede:

* Consultar empleados asignados.
* Supervisar asistencia.
* Consultar historial.
* Revisar información operativa.

No debe poder:

* Modificar configuraciones críticas.
* Gestionar permisos administrativos.
* Acceder a funcionalidades exclusivas del administrador.

---

# 11.3 Empleado

El empleado utiliza principalmente el sistema para registrar su actividad laboral.

Puede:

* Registrar ingreso.
* Registrar egreso.
* Consultar historial propio.
* Subir justificativos.
* Consultar información personal.

No puede acceder a información de otros empleados.

---

# 12. Reglas de negocio principales

## 12.1 Registro de asistencia

El sistema debe permitir registrar:

* Entrada.
* Salida.

Cada registro debe contener información suficiente para auditar el movimiento.

Datos esperados:

* Usuario.
* Fecha.
* Hora.
* Lugar.
* Coordenadas.
* Tipo de movimiento.
* Estado.
* Información adicional.

---

# 12.2 Control de doble registro

LOCUSTAF debe impedir múltiples registros inválidos.

Reglas:

* Un empleado no puede realizar dos ingresos en la misma jornada.
* No puede realizar una salida si no existe un ingreso previo.
* No puede registrar movimientos duplicados.

Actualmente esta protección se realiza mediante:

* Transacciones Firestore.
* Colección `_attendance_locks`.

---

# 12.3 Jornada laboral

La jornada laboral depende de la configuración asignada al empleado.

Debe contemplar:

* Turno asignado.
* Hora de inicio.
* Hora de finalización.
* Tolerancia permitida.

Ejemplo:

Turno mañana:

```text
Inicio: 08:00
Fin: 16:00
Tolerancia: 15 minutos
```

---

# 12.4 Validación de horario

El sistema debe poder determinar:

* Llegada puntual.
* Llegada tarde.
* Salida anticipada.
* Jornada completa.
* Horas extra.

Estados esperados:

| Estado     | Descripción                          |
| ---------- | ------------------------------------ |
| Puntual    | Ingreso dentro del horario permitido |
| Tarde      | Ingreso posterior a la tolerancia    |
| Completo   | Jornada realizada correctamente      |
| Incompleto | Falta uno de los movimientos         |
| Ausente    | No existe registro de ingreso        |

---

# 12.5 Tolerancia

Cada turno puede tener una tolerancia configurable.

Ejemplo:

Turno:

```text
08:00
```

Tolerancia:

```text
15 minutos
```

Resultado:

* Entrada 08:10 → Puntual.
* Entrada 08:20 → Tarde.

La tolerancia no debe estar fija en el código.

Debe ser configurable.

---

# 12.6 Horas trabajadas

El sistema debe calcular:

* Tiempo efectivo trabajado.
* Tiempo de jornada.
* Diferencia respecto al horario esperado.

Actualmente existe cálculo básico de duración.

Pendiente:

* Separar horas normales.
* Separar horas extra.
* Detectar jornadas incompletas.

---

# 12.7 Horas extra

Una jornada genera horas extra cuando:

La salida supera el horario final del turno asignado.

Ejemplo:

Turno:

```text
08:00 - 16:00
```

Salida:

```text
17:30
```

Resultado:

```text
1 hora 30 minutos extra
```

---

# 12.8 Asistencias incompletas

Debe detectarse cuando:

* Existe ingreso sin salida.
* Existe salida inválida.
* Falta información necesaria.

Ejemplo:

Empleado registra:

```text
08:02 Entrada
```

Pero nunca registra salida.

Resultado:

Estado:

```text
Incompleta
```

---

# 12.9 Ausencias

Una ausencia se determina cuando:

* Existe una jornada asignada.
* No existe registro de ingreso.
* No existe justificativo aprobado.

La ausencia debe poder relacionarse con:

* Fecha.
* Usuario.
* Turno.
* Motivo.

---

# 13. Geolocalización

La geolocalización es una funcionalidad central de LOCUSTAF.

Su objetivo es validar que el empleado se encuentra físicamente en un lugar autorizado.

---

# 13.1 Lugares de trabajo

Cada lugar debe contener:

* Nombre.
* Dirección.
* Latitud.
* Longitud.
* Radio permitido.
* Estado.

Ejemplo:

```text
Empresa Central

Latitud:
-34.560

Longitud:
-58.700

Radio:
50 metros
```

---

# 13.2 Validación de distancia

Al realizar asistencia:

El sistema debe:

1. Obtener ubicación actual del empleado.
2. Obtener ubicación del lugar asignado.
3. Calcular distancia.
4. Comparar con radio permitido.

Si está dentro del radio:

```text
Registro permitido
```

Si está fuera:

```text
Registro rechazado
```

---

# 13.3 Seguridad de ubicación

La ubicación no debe considerarse confiable únicamente desde el cliente.

Debe almacenarse información suficiente para auditoría.

Datos recomendados:

* Coordenadas registradas.
* Fecha.
* Hora.
* Lugar validado.
* Resultado de validación.

---

# 14. Justificativos

El módulo de justificativos permite respaldar situaciones donde un empleado no puede cumplir normalmente con su jornada.

No está limitado exclusivamente a documentación médica.

---

# 14.1 Tipos de justificativos

Ejemplos:

* Certificado médico.
* Permiso personal.
* Licencia.
* Constancia laboral.
* Comprobante externo.
* Otra documentación aceptada.

---

# 14.2 Flujo del justificativo

Flujo esperado:

Empleado:

1. Selecciona fecha.
2. Indica motivo.
3. Adjunta documentación.
4. Envía solicitud.

Administrador:

1. Revisa documentación.
2. Aprueba o rechaza.
3. Registra decisión.

---

# 14.3 Almacenamiento

Los archivos deben almacenarse mediante Firebase Storage.

La seguridad debe garantizar:

* Usuario autorizado puede subir documentos propios.
* Administradores pueden revisar documentación.
* Usuarios no autorizados no pueden acceder.

* Evitar reconstrucciones innecesarias de widgets.

# 28. Seguridad como principio de diseño

La interfaz nunca debe ser considerada una capa de seguridad.

Toda autorización debe estar respaldada por:

* Firestore Rules.
* Storage Rules.
* Validaciones de backend.

Ocultar un botón no equivale a bloquear una acción.

---

# 29. Objetivo final del diseño

La interfaz final de LOCUSTAF debe transmitir:

* Profesionalismo.
* Confianza.
* Facilidad de uso.
* Organización.
* Calidad empresarial.

El usuario final debe percibir el sistema como una herramienta lista para utilizar en una organización real.

# 30. Flujo de trabajo de desarrollo

Todo desarrollo nuevo sobre LOCUSTAF debe seguir un proceso ordenado para reducir errores y mantener la estabilidad del sistema.

El flujo recomendado es:

```
Análisis
   ↓
Planificación
   ↓
Implementación
   ↓
Validación
   ↓
Documentación
   ↓
Commit
```

---

# 31. Análisis previo obligatorio

Antes de modificar código existente se debe:

1. Leer la documentación relacionada.
2. Analizar la implementación actual.
3. Identificar dependencias.
4. Evaluar impacto del cambio.
5. Determinar archivos afectados.

No se deben realizar modificaciones masivas sin comprender previamente el funcionamiento actual.

---

# 32. Reglas para nuevas implementaciones

Toda nueva funcionalidad debe:

* Respetar la arquitectura existente.
* Integrarse con módulos actuales.
* Reutilizar componentes existentes cuando sea posible.
* Mantener separación de responsabilidades.
* Evitar duplicación.
* Mantener compatibilidad con Firebase.

---

# 33. Restricciones de modificación

No se deben realizar cambios de forma arbitraria sobre:

## Arquitectura

No cambiar:

* Feature First.
* Repository Pattern.
* Riverpod.
* GoRouter.

Sin una justificación técnica documentada.

---

## Tecnologías principales

No reemplazar:

* Flutter.
* Firebase.
* Cloud Firestore.
* Firebase Storage.

Sin una evaluación completa del impacto.

---

## Estructura

Evitar:

* Mover carpetas sin necesidad.
* Renombrar módulos completos.
* Crear estructuras paralelas.

---

# 34. Uso de herramientas de asistencia

Las herramientas de inteligencia artificial utilizadas durante el desarrollo deben trabajar bajo estos principios:

* Analizar antes de modificar.
* Explicar cambios realizados.
* Mantener coherencia con la documentación.
* No crear soluciones temporales innecesarias.
* No eliminar funcionalidades existentes.

La IA debe actuar como un desarrollador dentro del proyecto, no como un generador independiente de código.

---

```

Rediseña dashboard administrativo con Material 3

```

---

Incorrectos:

fix
```

```
update
```

```
cambios varios
```

```
arreglos
```

# 36. Tamaño de los commits

Los commits deben agrupar cambios relacionados.

Correcto:

```

Actualiza reglas Storage

Incorrecto:

```
Commit:
Implementa todo el sistema completo
```
